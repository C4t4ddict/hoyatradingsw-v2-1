# 웹·데스크톱 보안 개선 설계

## 요구사항

- SEC-1. Next.js와 Python 런타임 의존성을 패치하고 잠금/감사 결과와 호환성을 검증한다. 웹 기본 브랜치의 배포 기준도 확인한다.
- SEC-2. 기본 웹 런처는 루프백에 바인딩한다. 웹 API는 허용한 출처만 CORS로 허용하며 데스크톱은 기존 루프백 게이트웨이를 사용한다.
- SEC-3. 웹 변경 API에 설정 토큰을 적용한다. 전략 승인자는 서버에서 확인된 운영자 주체로 기록한다. 레거시 계정 조회와 변경은 토큰 미설정 시 거부한다. 데스크톱 토큰과 허용 목록으로 기존 모의투자가 동작하도록 한다.
- SEC-4. 웹과 데스크톱 응답에 렌더링과 호환되는 보안 헤더를 추가한다. 공개 시세와 뉴스, 백테스트에 사용하는 HTTPS 요청은 백엔드에서 계속 처리한다.
- SEC-5. 외부 피드의 목적지, 리다이렉트, 응답 크기와 XML 파싱을 제한한다. 모델 파일은 신뢰된 경로와 파일 무결성을 확인할 수 있도록 한다.
- SEC-6. CI 의존성을 검증 가능한 버전으로 고정하고 안전한 Windows 배포에 필요한 서명과 검증 절차를 명시한다. 실제 서명과 운영 TLS 확인에는 사용자 소유 인증서 또는 배포 정보가 필요하다.

## 검증

- 일반 빌드, 각 저장소 변경 범위 회귀 테스트, npm 및 Python 권고 재검사, Electron 테스트를 실행한다.
- 정상 공개 데이터 요청, 설정 토큰의 유효·무효 입력과 루프백 응답을 확인한다. 실제 주문과 거래소 비공개 API는 호출하지 않는다.

## 실행과 배포

- 웹 `3001`과 API `8010`은 기본적으로 이 PC에서만 받는다. 원격 운영은 HTTPS 리버스 프록시에서 접근 제어, TLS, HSTS와 요청 제한을 적용한다. `HOYA_WEB_HOSTS`에는 프록시가 백엔드에 전달하는 승인된 호스트를, `HOYA_WEB_ORIGINS`에는 승인된 브라우저 출처를 입력한다. `NEXT_PUBLIC_API_BASE_URL`은 API 주소 전용이고 토큰을 포함하면 안 된다.
- `SETTINGS_TOKEN`은 웹 모의투자 제어와 운영 변경/상세 조회에 사용한다. 웹 화면에서는 세션 메모리에만 입력을 보관한다. `WEBHOOK_TOKEN`은 별도 값으로 구성하며 비어 있거나 예제 값이면 관련 경로가 거부된다.
- 공개 뉴스는 HTTPS 공개 주소로만 연결한다. HTTP나 다른 게시자 호스트로의 리다이렉트는 거부한다. 공개 거래소 시세, 백테스트, 뉴스 수집 트래픽은 백엔드에서 나가며 브라우저 리스닝 범위와 별개다.
- 모델 폴더는 서비스 계정만 쓰도록 운영한다. 별도 읽기 전용 위치에 `HOYA_MODEL_HASH_MANIFEST`를 두고 `{"models_bidirectional/label_up_4h.joblib":"<SHA-256>"}`와 같은 키를 승인된 로컬 모델로 채우면 로드 전에 검증된다. 검증 후 재학습하는 경우 검토된 모델과 매니페스트를 함께 교체한다.
- Next 인라인 부트스트랩과 스타일 호환을 위해 현재 CSP의 스크립트와 스타일에는 인라인 허용이 있다. 프레임·객체·외부 스크립트/네트워크는 정책으로 제한한다.
- Windows CI는 체크섬 검사 후 Python 3.12.16 배포본을 사용한다. 공개 배포 시에는 사용자 소유 코드 서명 인증서로 최종 바이너리와 설치 파일을 타임스탬프와 함께 서명하고, Windows의 `Get-AuthenticodeSignature`로 `Valid`를 확인한 뒤 게시한다. 체크섬 검증은 Authenticode 서명과 별도로 수행한다.
